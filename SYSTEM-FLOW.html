01System Overview

BITBASH Sentry is a crypto price-surveillance terminal. You browse the top-100 market, ⭐-star coins into your watchlist, and a background engine inside the same Next.js server process watches them 24/7: every 15s it pulls prices from CoinGecko, compares each coin against its last-tick baseline, and fires a FLASH CRASH (≤ −2%) or PRICE SURGE (≥ +2%) alert into PostgreSQL. Browsers never call CoinGecko — they poll the server's RAM cache, so 100 open tabs cost zero extra external calls.

03Flow Walkthroughs — happy path + every edge the code actually handles

FLOW AUser logs in (email + password, with the Google variant)

The auth spine: how session.user.id ends up holding the Prisma cuid that every watchlist query keys on.

  1. login/page.tsx — form submit calls signIn("credentials", {email, password, redirect:false}) → browser POSTs /api/auth/callback/credentials. EDGE — redirect:false means the page handles failure inline (error banner) instead of NextAuth bouncing to an error URL.
  2. api/auth/[...nextauth]/route.ts — 6-line catch-all; hands every /api/auth/* request to NextAuth configured by lib/auth.ts.
  3. lib/auth.ts → authorize() — email.trim().toLowerCase(), then prisma.user.findUnique({where:{email}}). EDGE — user enumeration: unknown email returns null → the exact same generic failure as a wrong password. An attacker can't probe which emails have accounts. EDGE — Google-only account: password_hash === null → authorize() throws "This account uses Google Sign-In" instead of calling bcrypt.compare(pw, null).
  4. bcrypt.compare(password, user.password_hash) — wrong password → null → generic failure. Match → returns {id, email}.
  5. jwt() callback — runs only at the login moment (user param exists): one findUnique stamps token.dbId = dbUser.id. WHY — one DB hit per login, not per request. Every later request just decodes the JWT; token.sub would hold Google's id for OAuth users, so the app carries its own dbId.
  6. NextAuth signs the JWT → httpOnly Set-Cookie → login page routes to /dashboard.
  7. middleware.ts — every later request to a guarded path: valid cookie → pass; missing/expired → 307 /login?callbackUrl=…. EDGE — raw API calls: every guarded route re-checks getServerSession() itself, so curl without a cookie gets clean 401 {error:"Unauthorized"} JSON — never a 307 to an HTML login page.
  8. session() callback — every getServerSession() / useSession() copies token.dbId → session.user.id. That id is what Flow B keys on.

Google variant — steps 3–4 become the signIn() callback: prisma.user.upsert keyed by email. Edges handled there: existing manual account → Google gets linked (google_id attached), not a P2002 duplicate-email crash · Google profile without an email → refused (return false) · upsert fails (DB down) → sign-in blocked rather than minting a session for a user that isn't persisted. Signup edges (api/auth/signup): server-side passkey rules mirror the form — the form can be bypassed with curl, the server can't · Google-only email trying to register → told to use Google · two simultaneous signups on one email → the DB unique constraint fires P2002 → mapped to the normal "already exists" 400, not a raw 500.

FLOW BUser stars a coin on /market

The ONLY write that couples Lane 2 (browsing) to Lane 1 (surveillance) — and it couples through the database, never a direct call.

  1. MarketTable.tsx → toggleStar() — flips the star optimistically (instant UI), then POST /api/watchlist {asset_id, name}. EDGE — request fails (offline, 401, 500): functional state update rolls the star back to exactly its previous state + red toast "Couldn't add Bitcoin — try again". The UI never lies about what's persisted.
  2. middleware.ts checks the JWT; api/watchlist/route.ts → POST() re-checks getServerSession(). EDGE — malformed body: req.json() throws on bad JSON → caught → clean 400 {error:"Invalid JSON body"}. Missing/blank asset_id or name → 400. No 500 stack traces from user input.
  3. prisma.watchlist.upsert() on the @@unique([user_id, asset_id]) pair. EDGE — double-click / retry after timeout: the second write hits update:{} — a harmless no-op. Without upsert this would be a P2002 crash on every double-star.
  4. Point zero: one-off fetchWatchlistPrices([asset_id]) → detector.ts → seedBaseline(asset_id, price) so the detector can compare on the very next 15s tick. EDGE — seed fails (CoinGecko down): logged, swallowed — the star STILL succeeds; the poller seeds the baseline on its next tick instead. EDGE — coin already tracked: seedBaseline returns early if a baseline exists. Baselines are GLOBAL (keyed by asset_id) — a second user starring Bitcoin must not reset a live baseline mid-window and mask an in-progress crash. Also refuses price ≤ 0 — bad data never poisons a baseline.
  5. {success:true} → green toast via Toaster.tsx: "Bitcoin added to watchlist".
  6. ≤15s later: poller.ts → getCoinsToTrack() re-reads the table (distinct — 50 users watching bitcoin = 1 id) and the coin joins the surveillance set. No events, no queue — the shared table IS the contract.
  7. /watchlist shows it: SSR merges Postgres rows with getCache(); WatchlistView.tsx keeps it live at 5s. EDGE — first 15s gap: if the poller hasn't ticked yet, SSR builds a placeholder card (name from DB, price 0) that the 5s poll fills — the page never blocks waiting for a price.

FLOW CA flash-crash alert is born (no user action at all)

The core loop — runs 24/7 whether any browser is open or not. Chain: instrumentation.ts → poller.ts → coingecko.ts → detector.ts → Postgres + cache.ts → browsers.

▦ The detection formula — detector.ts, line by line

// for EVERY coin in the tick's snapshot:
movePct = ((currentPrice − baselinePrice) / baselinePrice) × 100

FLASH CRASH  if movePct ≤ CRASH_THRESHOLD_PCT   // spec −2.0 · TEST MODE −0.01
PRICE SURGE  if movePct ≥ SURGE_THRESHOLD_PCT   // spec +2.0 · TEST MODE +0.01

// afterwards, ALWAYS (alert or not):
baselinePrice ← currentPrice   // this tick becomes next tick's yardstick

Worked example — Pepe, baseline $0.00001000, current tick reads $0.00000972:

movePct = ((0.00000972 − 0.00001000) / 0.00001000) × 100 = −2.8%
−2.8 ≤ −2.0  →  FLASH CRASH
INSERT CryptoAlert { asset_id:'pepe', price_at_drop:0.00000972, drop_percentage:−2.8 }
baseline['pepe'] ← 0.00000972   // a further −2% from HERE fires again after cooldown

Why baseline resets every tick: the formula measures tick-over-tick velocity (a ~15s window), not distance from a 24h open. A slow bleed of −0.3% per tick never alerts — only a sudden move inside one window does. That's what makes it a flash-crash detector.

  • No baseline yet (first time seen) → seed it and skip comparison — never compare against nothing.
  • price ≤ 0 or missing → coin skipped entirely; garbage data can't fire alerts or poison baselines.
  • 60s cooldown per (coin, direction) — __lastAlertTime / __lastSurgeTime maps. A crash and a surge on the same coin are independent; one crash can't spam 4 rows in a minute.
  • DB-level dedup — before insert, check for a recent same-direction alert for this asset; a restarting server can't double-write.
  • Alert insert fails (DB offline) → caught + logged; the tick continues, prices still reach the cache.
  • Whole batch fetch fails → pollOnce() throws → cache is NOT overwritten; browsers keep the last good snapshot and updatedAt goes stale (visible in UI).
  1. Boot (once): instrumentation.ts → register() — only when NEXT_RUNTIME === "nodejs" — calls startPoller(). globalThis.__pollerStarted guard: dev HMR reloads modules but never spawns a second timer.
  2. Tick (every 15s): poller.ts → pollOnce() → SELECT DISTINCT asset_id FROM Watchlist. EDGE — empty watchlists: zero ids → tick exits immediately. No users watching = zero CoinGecko spend.
  3. Prices, parity-first: coins inside the top-100 are lifted from the SAME fetchMarkets() snapshot the /market table serves (a coin can never show two prices on two pages); only coins outside the top-100 get a direct ?ids= batch (≤100 ids per call).
  4. detector.ts → detectCrashes(coins) — the formula box above, per coin, both directions.
  5. Threshold breached + cooldown clear + no recent DB duplicate → prisma.cryptoAlert.create() with sign-encoded drop_percentage (− crash, + surge) → cooldown timestamp updated → logged to logs/app-*.log.
  6. cache.ts → setCache(coins, crashes, surges) — wholesale replace of __priceStore with fresh updatedAt. Un-starred coins simply aren't in the new array — no cleanup code needed.
  7. Browsers find out by polling (no push/websocket): within 5s WatchlistView paints the card red/green with a pulse, and AlertsView / DashboardLive pick the row up from GET /api/alerts. Worst-case end-to-end latency ≈ 15s (tick) + 5s (poll).
